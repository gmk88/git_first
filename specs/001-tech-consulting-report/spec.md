# Feature Specification: 企业技术咨询报告系统

**Feature Branch**: `001-tech-consulting-report`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "我需要一个企业官网级别的系统，主要是对一些企业做技术质询服务，最终产品形态是一份书面报告。"

## Clarifications

### Session 2026-11-05

- Q: 咨询申请的阶段流转除了单向推进外，是否允许回退到早前阶段？ → A: 允许回退到
  任意早前阶段；回退必须填写原因，与推进一样记录流转历史。
- Q: 顾问上传报告后如果发现报告有误需要更正，系统应如何处理已上传的报告文件？ → A:
  保留全部历史版本；新版本上传后旧版本自动归档，客户只能下载最新版。
- Q: 申请编号将展示给访客并用于客户查询报告，它应采用哪种格式？ → A: 日期 + 当日
  递增序号（如 20261105-0001）；编号仅作为面向人的业务参考号，资源的实际访问定位
  使用不可枚举的内部标识并仍需凭证校验。
- Q: 访客提交的咨询申请包含企业名称、联系人、电话、邮箱等个人信息，系统需要哪种
  程度的个人信息保护承诺？ → A: 仅站内使用 —— 个人信息仅用于本次咨询服务联系，
  不在官网公开展示、不提供给第三方。
- Q: 系统对外服务的可用性需要达到什么目标？ → A: 尽力而为 —— 无正式 SLA 承诺，
  故障在工作时间内修复。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 访客了解咨询服务并提交咨询申请 (Priority: P1)

一位企业负责人打开公司官网，浏览首页了解技术咨询服务的内容、服务流程和
公司背景，随后通过咨询申请表单留下企业名称、联系方式和咨询需求描述并提交。
系统确认受理后，访客知道自己的申请已被接收、后续会有顾问联系。

**Why this priority**: 这是整个系统的获客入口和唯一收入来源起点；没有咨询申请，
后续所有咨询与报告交付都无从发生。它独立构成一个可上线的最小官网。

**Independent Test**: 从首页浏览开始，完成表单填写与提交，收到受理确认，
全程无需其他功能即可独立验证并演示。

**Acceptance Scenarios**:

1. **Given** 访客打开首页，**When** 浏览首页各区块（服务介绍、服务流程、关于我们、
   联系方式），**Then** 页面完整展示这些内容且无需登录。
2. **Given** 访客处于申请表单页，**When** 填写所有必填字段并提交，**Then** 系统显示
   受理成功提示，并生成唯一的申请编号展示给访客。
3. **Given** 访客未填必填字段或邮箱/电话格式不正确，**When** 提交表单，**Then**
   系统逐字段提示具体错误，且已填内容不丢失。

---

### User Story 2 - 顾问受理咨询并完成咨询交付报告 (Priority: P2)

一位顾问登录管理系统，查看待处理咨询申请列表，接手一条申请，将其推进
"受理 → 评估 → 执行咨询 → 报告撰写 → 报告交付"的阶段流程。咨询过程中记录
与企业的沟通纪要，最后产出书面咨询报告，将报告文件交付给该客户。

**Why this priority**: 这是服务的核心交付流程，是产品价值所在；但它依赖
Story 1 产生的申请数据，故排在第二。实现后系统从"官网"升级为"业务管理系统"。

**Independent Test**: 使用预置的申请数据登录后台，走完从受理到报告交付的
全流程，可独立验证而无需依赖前端官网访客流程。

**Acceptance Scenarios**:

1. **Given** 顾问已登录管理系统，**When** 打开咨询申请列表，**Then** 可看到每条
   申请的企业名称、联系人、提交时间、当前阶段与负责人，并支持按阶段/时间筛选。
2. **Given** 一条处于"待受理"状态的申请，**When** 顾问将其认领并推进到下一阶段，
   **Then** 申请阶段状态更新并记录操作时间与操作人。
3. **Given** 顾问在咨询过程中，**When** 添加一条沟通纪要（时间、方式、内容摘要），
   **Then** 纪要按时间顺序保存在该申请下，可查看历史记录且不可修改删除。
4. **Given** 顾问已完成报告文件，**When** 上传报告并标记该申请为"已交付"，
   **Then** 系统记录交付时间，申请进入终态。
5. **Given** 一条处于"评估"阶段的申请，**When** 顾问选择回退到"受理"阶段并填写
   原因，**Then** 申请阶段变更为"受理"，回退原因与操作人、操作时间一并记录在
   流转历史中。

---

### User Story 3 - 客户在线查看已交付的咨询报告 (Priority: P3)

企业客户收到顾问提供的报告访问凭证后，在官网的报告查询页输入申请编号和
凭证（或登录客户账户），查看并下载属于自己企业的已交付咨询报告。

**Why this priority**: 提升交付体验与专业形象，属于增值能力；不影响咨询服务
本身的发生（顾问可通过邮件等线下方式交付），故为 P3。

**Independent Test**: 使用一条已交付的申请数据与访问凭证，在报告查询页
完成查看与下载，可独立验证。

**Acceptance Scenarios**:

1. **Given** 一条申请已交付报告且客户持有凭证，**When** 客户在查询页输入申请编号
   和凭证，**Then** 系统展示报告基本信息（企业名称、报告标题、交付日期）并提供
   下载入口。
2. **Given** 客户输入的申请编号或凭证错误，**When** 提交查询，**Then** 系统提示
   "编号或凭证不正确"，不透露该编号是否存在。
3. **Given** 客户正在查看报告详情，**When** 连续 5 次查询失败，**Then** 该编号
   的查询被临时锁定 15 分钟。

---

### Edge Cases

- 同一企业重复提交咨询申请时，系统如何处理？→ 允许重复提交（不同需求各自成单），
  由顾问在受理阶段人工合并或关闭。
- 访客在表单中提交超长文本或非预期字符时？→ 系统按字段长度上限截断或拒绝，
  并给出明确提示，不得静默丢弃。
- 顾问离职/转让申请时？→ 管理员可将申请重新指派给其他顾问，历史操作记录保留
  原操作人。
- 报告文件上传失败或中途断网时？→ 系统提示上传失败，申请保持"报告撰写"阶段，
  顾问可重试。
- 客户在报告交付后长期未查看？→ 报告查询入口长期有效；凭证泄露重置由管理员
  手动处理。
- 顾问交付后发现报告有误需更正？→ 上传新版本报告，旧版本自动归档；客户查询页
  仅展示并允许下载最新版本。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供无需登录即可访问的官网首页，包含：服务介绍、服务流程、
  关于我们、联系方式四个内容区块。
- **FR-002**: 系统 MUST 提供咨询申请表单，必填字段：企业名称、联系人、联系电话、
  邮箱、咨询需求描述；非必填字段：期望完成时间。表单页 MUST 展示个人信息保护
  说明：所填信息仅用于本次咨询服务联系，不在官网公开展示、不提供给第三方。
- **FR-003**: 系统 MUST 在提交时校验必填项完整性及邮箱、电话格式，校验失败时
  逐字段返回错误信息且保留已填内容。
- **FR-004**: 系统 MUST 为每条提交成功的申请生成唯一申请编号，并向访客展示。编号
  格式 MUST 为"日期 + 当日递增序号"（如 20261105-0001）。申请编号仅作为面向人的
  业务参考号；报告等资源的实际访问定位 MUST 使用不可枚举的内部标识，且 MUST 同时
  校验凭证（见 FR-010–FR-012），以满足项目宪法对不可枚举对外标识的要求。
- **FR-005**: 系统 MUST 提供顾问/管理员登录入口，登录 MUST 基于账户名与密码，
  密码 MUST 以不可逆加密形式存储。
- **FR-006**: 系统 MUST 提供咨询申请管理列表，支持查看企业名称、联系人、提交时间、
  当前阶段、负责人，并支持按阶段和提交时间筛选与排序。
- **FR-007**: 系统 MUST 支持咨询申请的阶段流转：待受理 → 受理 → 评估 → 执行咨询 →
  报告撰写 → 已交付；每次流转 MUST 记录操作人与操作时间。允许回退到任意早前阶段，
  回退时 MUST 填写回退原因，并同样记录流转历史。
- **FR-008**: 系统 MUST 支持为申请添加不可修改、不可删除的沟通纪要（时间、沟通方式、
  内容摘要、记录人）。
- **FR-009**: 系统 MUST 支持为申请上传报告文件，仅允许 PDF / Word 文档
  （doc、docx），单一文件上限 50MB。同一申请允许上传新版本报告：旧版本 MUST 自动
  归档保留，客户查询页 MUST 仅提供最新版本的下载。
- **FR-010**: 系统 MUST 在报告上传后为该申请生成报告查询凭证，凭证 MUST 仅以
  明文形式展示一次，存储形式为不可逆加密。
- **FR-011**: 系统 MUST 提供面向客户的报告查询页，凭申请编号 + 凭证查询并下载
  已交付的报告；同一编号连续 5 次查询失败 MUST 锁定 15 分钟。
- **FR-012**: 系统 MUST 对报告文件的下载进行访问控制，未持有有效凭证的用户
  MUST 无法获取报告内容。
- **FR-013**: 管理员 MUST 能够将申请重新指派给其他顾问，历史操作记录中的操作人
  MUST 保持为原操作人。
- **FR-014**: 系统 MUST 记录安全相关事件（登录成功/失败、凭证查询失败、报告下载）
  的时间、账户或编号与来源，且此类日志 MUST 保留至少 180 天。
- **FR-018**: 系统 MUST NOT 在任何公开页面展示咨询申请中的个人信息（企业名称、
  联系人、电话、邮箱）；此类信息仅限后台顾问/管理员及本人通过编号+凭证查询时
  涉及的最小范围使用。
- **FR-015**: 系统 MUST 支持顾问在后台编辑官网的四个内容区块文案（服务介绍、服务
  流程、关于我们、联系方式），保存后官网立即生效。

- **FR-016**: 顾问账户 MUST 仅由管理员在后台创建，系统 MUST NOT 提供顾问自助
  注册入口。
- **FR-017**: 报告文件格式 MUST 限定为 PDF 与 Word（doc、docx）；其他格式的
  上传 MUST 被拒绝并提示支持的格式。

### Key Entities *(include if feature involves data)*

- **咨询申请（Consultation Request）**：一条企业咨询需求，包含企业名称、联系人、
  联系电话、邮箱、需求描述、期望完成时间、申请编号、当前阶段、负责人、提交时间。
  申请编号采用"日期 + 当日递增序号"格式（如 20261105-0001），仅作为业务参考号。
  阶段流转与沟通纪要都挂靠在申请之下。
- **阶段流转记录（Stage Transition Record）**：申请每次阶段变更（推进或回退）的
  一条不可变记录，包含前阶段、后阶段、操作人、操作时间；回退记录额外包含回退原因。
- **沟通纪要（Communication Note）**：咨询过程中与企业的沟通摘要，包含沟通时间、
  沟通方式、内容摘要、记录人、创建时间；不可修改、不可删除。
- **咨询报告（Consultation Report）**：申请最终交付物，每个申请可含多个版本：
  最新版本对客户可见，历史版本自动归档（不可被客户下载，顾问可查看）。每个版本
  包含报告文件、报告标题、上传人、上传时间；申请级别包含查询凭证（密文）、
  交付时间。
- **用户账户（User Account）**：顾问或管理员，包含账户名、密码（密文）、角色
  （顾问/管理员）、创建时间。
- **官网内容区块（Site Content Block）**：首页四个区块的可编辑文案，包含区块标识、
  标题、正文、最近更新时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一位新访客从打开首页到完成咨询申请提交并获得申请编号，全程不超过
  3 分钟。
- **SC-002**: 90% 的表单提交在访客首次尝试即通过校验（格式提示清晰、错误可定位）。
- **SC-003**: 顾问从登录到认领一条新申请并推进一个阶段，全程不超过 1 分钟。
- **SC-004**: 从咨询受理到报告交付的全流程（含各阶段流转与纪要记录）可在系统内
  完整追溯，任意申请可回放完整时间线。
- **SC-005**: 持有正确编号与凭证的客户，从打开查询页到开始下载报告不超过 1 分钟。
- **SC-006**: 未持有凭证的外部用户对报告的访问尝试 100% 被拒绝且被记录。
- **SC-007**: 系统在 100 并发访客浏览官网与提交申请时无功能故障，页面打开时间
  在常规网络下低于 3 秒。
- **SC-008**: 任意公开页面（首页、表单、查询页）经审查均不泄露任何咨询申请的
  个人信息，100% 符合"仅站内使用"承诺。

## Assumptions

- 访客与客户不注册账户：客户通过"申请编号 + 凭证"访问报告（凭证由顾问在交付时
  线下告知客户）。
- 顾问与管理员使用同一后台，权限差异仅体现在：管理员可管理账户（含创建顾问账户，
  见 FR-016）与重新指派申请，顾问仅可操作自己名下的申请。
- 报告以文件上传/下载方式交付，系统不提供在线编辑报告内容的功能。
- 沟通纪要的"不可修改删除"指系统层面禁止；不涉及外部备份恢复等运维场景。
- 单套系统服务单一咨询公司；不做多租户。
- 初始内容规模小（日申请量 < 100），无高并发报表或数据分析需求。
- 官网为单语言（中文）站点。
- 可用性目标为尽力而为：无正式 SLA 承诺，故障在工作时间内修复；不为此构建
  高可用架构。

## Dependencies

- 咨询申请（Story 1）是后台管理（Story 2）与报告查询（Story 3）的数据前提。
- 报告查询（Story 3）依赖 Story 2 的报告上传与凭证生成。
- 无外部系统集成；邮件通知等能力不在本特性范围内。

## Out of Scope

- 在线支付、合同签订、发票等交易功能。
- 站内即时通讯、邮件/短信自动通知。
- 报告在线编辑、协同撰写、版本管理。
- 多语言、多租户、数据分析报表。
- 客户账户体系与自动注册。
